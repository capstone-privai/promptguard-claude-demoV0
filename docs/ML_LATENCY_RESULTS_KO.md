# ML 탐지기 지연 측정 결과 (ml-span v10, ml-v9)

**모든 수치는 PC 한 대 기준이다.** Windows 11, 논리 코어 8개, Python 3.14, torch 2.15 CPU, onnxruntime 1.31.1. 2026-11-10 측정. 다른 PC에서는 값이 달라지며, 같은 PC에서도 실행마다 흔들린다(6절 참고). 재현은 `tests/performance/ml_bench.py`로 한다. 시간 단위는 ms이고 표기는 p50 / p95 / max다.

## 요약

| 질문 | 답 |
|---|---|
| int8 양자화를 쓸 수 있나 | 쓸 수 없다. v10은 recall이 1.8~4.7%p, v9는 14.5~24.6%p 떨어져 1%p 기준에 걸린다. |
| 어떤 조합이 가장 빠른가 | fp32 ONNX, 스레드 2개, 단서 주변 방식, 길이 한도 4,000자. 호출 p95 842~1,014ms, 360회 중 차단 0회, 5초 초과 0회. |
| 빠른 탐지기가 덮은 줄을 건너뛰면 | 이득이 없다. p95는 그대로이고 recall만 2.5%p 줄었다. |
| 후보 줄 방식은 | 지금 형태로는 쓸 수 없다. recall은 오르지만 호출의 32%가 차단되고 무관한 줄 오탐이 약 20배다. |
| 기본으로 켜도 되나 | 시간만 보면 가능하다. 다만 시간 외 조건이 남아 있어 이번 결과만으로 켜는 것은 권하지 않는다(7절). |

## 1. 기준선 (지금 main)

실제 워커에 HTTP `/scan-batch`로 항목 1개를 보냈다. 조건마다 30회, 입력은 이 저장소의 git log, package-lock, 소스, metrics, ls를 섞은 글이다.

| 입력 | ML 꺼짐 | ml-v9 | ml-span |

| 200B 비밀 없음 | 480 / 604 / 927 | 543 / 687 / 757 | 687 / 757 / 772 |
| 200B 비밀 있음 | 483 / 565 / 854 | 596 / 679 / 775 | 458 / 543 / 716 |
| 2KB 비밀 없음 | 496 / 592 / 878 | 589 / 1,485 / 1,800 | 680 / 1,448 / 1,784 |
| 2KB 비밀 있음 | 673 / 734 / 757 | 542 / 1,299 / 1,492 | 617 / 1,284 / 1,568 |
| 20KB 비밀 없음 | 763 / 839 / 1,123 | 761 / 2,175 / 2,477 | 755 / 2,084 / 2,388 |
| 20KB 비밀 있음 | 788 / 917 / 1,079 | 789 / 1,851 / 4,097 | 835 / 2,485 / 4,101 |
| 차단 / 5초 초과 | 0 / 0 | 1 / 0 | 1 / 0 |

| 워커 시작 | ML 꺼짐 | ml-v9 | ml-span |
|---|---|---|---|
| 준비까지 시간 | 10,138 | 26,944 | 22,231 |

- 실제로 먼저 걸리는 한도는 5초 브리지가 아니라 ML 어댑터의 4초다. 차단은 모두 약 4,100ms에서 나왔다.
- Mod와 Guard가 워커를 하나씩 띄우므로 실제 메모리는 모델당 약 2배이고, 한 tool 왕복에 스캔이 2번 있다. 이 표는 그중 1번이다.

## 2. 양자화 (ml-span, ml-v9)

ONNX는 opset 18로 내보냈고, int8은 onnxruntime `quantize_dynamic(QInt8)`이다. 경계 보정(`boundary.pt`)은 그대로 PyTorch다. 파일 크기는 fp32 537MB, int8 134MB. 가중치와 ONNX 파일은 `.runtime/ml-bench`에만 있고 git에 없다.

같은 입력으로 ML만 잰 시간이다.

| 모델 | 방식 | 200자 | 2,000자 | 6,000자 |
|---|---|---|---|---|
| ml-span | fp32 PyTorch | 70 / 100 / 160 | 714 / 994 / 1,044 | 2,441 / 3,479 / 3,978 |
| ml-span | fp32 ONNX | 59 / 88 / 171 | 661 / 859 / 964 | 1,966 / 2,510 / 2,665 |
| ml-span | int8 ONNX | 34 / 71 / 101 | 339 / 511 / 624 | 1,033 / 1,382 / 1,741 |
| ml-v9 | fp32 PyTorch | 70 / 108 / 131 | 643 / 745 / 883 | 1,874 / 2,284 / 2,470 |
| ml-v9 | fp32 ONNX | 45 / 61 / 309 | 512 / 724 / 1,289 | 1,618 / 1,952 / 2,203 |
| ml-v9 | int8 ONNX | 32 / 118 / 350 | 312 / 579 / 840 | 1,239 / 2,678 / 3,357 |

## 3. 정확도: int8은 채택하지 않는다

`promptguard-model`의 합성 분리 평가셋 전체를 썼다. `data/span-holdout-v11/test.jsonl`(504행), `data/span-context-v10/test.jsonl`(504행), `data/span-negative-challenge-v1/test.jsonl`(96행). 값 하나는 정답과 겹치면 찾은 것으로 셌다.

| 모델 | 평가셋 | 방식 | recall | 정답과 경계 일치 | precision | 음성 행 오탐 | PyTorch와 span 동일 |
|---|---|---|---|---|---|---|---|
| ml-span | holdout-v11 | PyTorch | 90.22% | 88.41% | 76.15% | 39/252 | - |
| ml-span | holdout-v11 | fp32 ONNX | 90.22% | 88.41% | 76.15% | 39/252 | 100% |
| ml-span | holdout-v11 | int8 | **85.51%** | 84.42% | 78.67% | 30/252 | 94.05% |
| ml-span | context-v10 | PyTorch | 92.75% | 88.41% | 96.25% | 10/252 | - |
| ml-span | context-v10 | fp32 ONNX | 92.75% | 88.41% | 96.25% | 10/252 | 100% |
| ml-span | context-v10 | int8 | **90.94%** | 88.41% | 99.21% | 1/252 | 96.63% |
| ml-v9 | holdout-v11 | PyTorch | 81.52% | 79.35% | 73.53% | 30/252 | - |
| ml-v9 | holdout-v11 | fp32 ONNX | 81.52% | 79.35% | 73.53% | 30/252 | 100% |
| ml-v9 | holdout-v11 | int8 | **67.03%** | 65.22% | 79.40% | 18/252 | 83.93% |
| ml-v9 | context-v10 | PyTorch | 80.07% | 77.54% | 90.95% | 12/252 | - |
| ml-v9 | context-v10 | fp32 ONNX | 80.07% | 77.54% | 90.95% | 12/252 | 100% |
| ml-v9 | context-v10 | int8 | **55.43%** | 53.99% | 83.15% | 16/252 | 82.54% |

- recall 변화: ml-span -4.7%p, -1.8%p / ml-v9 -14.5%p, -24.6%p. 네 경우 모두 1%p를 넘어 **두 모델 모두 int8을 채택하지 않는다.**
- negative-challenge는 모든 방식에서 96행 중 오탐 0행이었다.
- int8은 찾는 값의 개수 자체가 줄었다. v9의 임계값은 0.9997, v10은 0.9857로 1에 가까워서, 양자화로 점수가 조금만 내려가도 임계값 아래로 떨어진 것으로 보인다. 원인을 따로 검증하지는 않았다.

## 4. CPU 설정 (ml-span, 2,000자와 6,000자 섞음)

조건마다 혼자 60회, 나머지 30회. 6,000자 입력이 절반이라 1·2·6절의 일반 호출보다 훨씬 무거운 조건이다.

| 방식 | 스레드 | 혼자 | 빠른 탐지기와 함께 | 모델 2개 동시 |
|---|---|---|---|---|
| fp32 | 1 | 5,948 / 14,124 / 16,758 | 6,054 / 13,577 / 14,640 | 6,071 / 13,301 / 14,104 |
| fp32 | 2 | 3,097 / 7,238 / 7,769 | 3,096 / 7,492 / 7,622 | 3,476 / 7,893 / 8,158 |
| fp32 | 4 | 1,786 / 4,297 / 4,510 | 1,986 / 4,055 / 4,176 | 6,323 / 12,154 / 14,715 |
| fp32 | 8 | 3,704 / 9,164 / 9,658 | 4,454 / 10,036 / 10,711 | 11,786 / 24,664 / 25,462 |
| int8 (참고) | 1 | 2,505 / 6,879 / 7,541 | 2,856 / 6,325 / 6,502 | 2,563 / 6,421 / 7,998 |
| int8 (참고) | 2 | 1,127 / 2,201 / 2,642 | 1,048 / 2,953 / (이상값) | 1,143 / 2,802 / 2,988 |
| int8 (참고) | 4 | 582 / 3,666 / 3,824 | 2,337 / 4,376 / 4,711 | 5,020 / 11,274 / 13,039 |
| int8 (참고) | 8 | 4,920 / 12,218 / 14,713 | 4,821 / 11,491 / 11,886 | 4,431 / 7,321 / 9,740 |

- 혼자라면 4스레드가 가장 빠르지만, 모델 2개가 겹치면 4스레드는 2스레드보다 1.5배 이상 느려진다. 8스레드는 모든 경우에 4스레드보다 느렸다.
- 이상값: int8 2스레드 측정 중 max 1,885,851ms(약 31분) 한 건은 PC가 잠든 구간으로 보여 표에서 뺐다. int8은 채택하지 않아 결론에 영향이 없다.

## 5. 실행 순서: 덮인 줄 건너뛰기, 후보 줄 방식

20KB 혼합 글 안에 평가셋 한 행을 끼워 넣었다. holdout-v11 4행마다 1행과 negative-challenge 2행마다 1행, 합계 174행이다. 정답 값은 120개다. fp32 ONNX로 쟀다(PyTorch와 span이 같다는 것을 3절에서 확인). 찾은 값은 빠른 탐지기 결과와 합친 수다.

| 방식 | 찾은 값 | ML로만 찾음 | ML 시간 | ML이 읽은 글자 p50 | 음성 행 오탐 | 무관한 줄 오탐/글 1개 |
|---|---|---|---|---|---|---|
| 단서 주변 (지금) | 93/120 (77.5%) | 55 | 198 / 3,357 / 8,168 | 326 | 5/66 | 0.06 |
| 단서 주변 - 덮인 줄 제외 | 90/120 (75.0%) | 52 | 79 / 3,343 / 8,310 | 284 | 4/66 | 0.05 |
| 후보 줄 (전체) | 102/120 (85.0%) | 64 | 1,379 / 15,513 / 20,572 | 5,940 | 5/66 | 1.18 |
| 후보 줄 (단서·문장만) | 97/120 (80.8%) | 59 | 1,357 / 16,001 / 18,161 | 5,908 | 6/66 | 1.17 |

참고로 빠른 탐지기만으로는 38/120 (31.7%), ML이 행 하나만 따로 읽을 때 합집합은 110/120 (91.7%)이다.

- 덮인 줄 제외는 p95를 줄이지 못하고 3개를 놓쳤다. 무거운 호출은 애초에 단서 줄이 많은 호출이라서 일부를 빼도 줄지 않는다.
- 후보 줄의 recall에는 시간 초과가 반영되어 있지 않다. 6절처럼 4초 제한을 걸면 호출의 32%가 차단되므로 그대로 쓸 수 없다.
- 길이 한도를 줄이면 지금 방식의 찾은 값은 6,000자 93 → 4,000자 91 → 3,000자 88이다.

## 6. 결론: tool 호출 1회

실제 탐지기 앙상블(gitleaks 포함, 병렬 실행, 4초 제한 그대로)을 같은 프로세스에서 불렀다. 조합마다 200B, 2KB, 20KB, 비밀 있음/없음 각 30회, 합계 180회다. 측정은 세 차례로 나눠 했고, 3차는 전원이 꺼졌다가 재부팅한 직후다.

| 조합 (모두 단서 주변 방식) | 차수 | p50 | p95 | max | 차단 | 4초 초과 | 5초 초과 |
|---|---|---|---|---|---|---|---|
| ML 꺼짐 | 1 | 343 | 515 | 1,186 | 0 | 0 | 0 |
| PyTorch, 기본 스레드, 6,000자 (지금) | 1 | 329 | 1,427 | 4,081 | 1 | 1 | 0 |
| 같은 조합 재측정 | 2 | 370 | 1,454 | 4,078 | 1 | 1 | 0 |
| PyTorch, 2스레드, 6,000자 | 3 | 613 | 4,053 | 4,241 | 11 | 12 | 0 |
| PyTorch, 2스레드, 4,000자 | 3 | 391 | 2,026 | 4,116 | 0 | 1 | 0 |
| PyTorch, 기본 스레드, 3,000자 | 3 | 401 | 4,059 | 6,621 | 10 | 11 | 2 |
| fp32 ONNX, 기본 스레드, 6,000자 | 1 | 794 | 4,159 | 9,494 | 16 | 17 | 1 |
| fp32 ONNX, 기본 스레드, 4,000자 | 1 | 758 | 4,035 | 5,649 | 9 | 11 | 1 |
| fp32 ONNX, 기본 스레드, 3,000자 | 1 | 740 | 3,964 | 4,136 | 7 | 9 | 0 |
| fp32 ONNX, 4스레드, 6,000자 | 1 | 481 | 1,851 | 4,129 | 2 | 2 | 0 |
| fp32 ONNX, 2스레드, 6,000자 | 1 | 371 | 1,087 | 4,084 | 1 | 2 | 0 |
| 같은 조합 재측정 | 2 | 432 | 1,383 | 3,315 | 0 | 0 | 0 |
| **fp32 ONNX, 2스레드, 4,000자** | 2 | **337** | **842** | 1,312 | **0** | **0** | **0** |
| 같은 조합 재측정 | 3 | 369 | 1,014 | 1,447 | 0 | 0 | 0 |
| fp32 ONNX, 2스레드, 3,000자 | 2 | 330 | 817 | 1,401 | 0 | 0 | 0 |
| fp32 ONNX, 기본 스레드, 후보 줄 (단서·문장) | 1 | 1,219 | 6,771 | 19,553 | 58 | 60 | 16 |

**기본으로 켠다면 권장 조합: fp32 ONNX, intra_op 2, 단서 주변 방식, 길이 한도 4,000자.**

- tool 호출 1회 p95는 842~1,014ms다. 위 수치는 HTTP를 뺀 값이고, 1절과 비교한 HTTP와 워커 비용은 ML 꺼짐 기준 약 150~450ms이므로 실제로는 약 1.0~1.5초로 보면 된다.
- 5초 한도에 걸린 비율은 360회 중 0회, 4초 차단도 0회다. 0회여도 이 표본으로는 실제 비율이 약 0.8%까지일 수 있다.
- 4,000자 한도의 대가는 5절의 찾은 값 93 → 91이다. 한도를 넘는 호출은 ML만 건너뛰고 빠른 탐지기는 그대로 돈다. recall을 우선하면 6,000자로 두고 호출 p95 1,087~1,383ms, 차단 1/360을 받아들이면 된다. 다만 2스레드에서 6,000자를 다 읽으면 5~7초가 걸려(4절) 그런 호출은 4초 제한에 차단된다. 이 말뭉치에는 그런 입력이 드물었을 뿐이다.

읽을 때 주의할 점:

- **기본 스레드를 그대로 쓰면 ONNX가 오히려 느리다.** fp32 기본 스레드는 차단 16/180으로 지금 PyTorch보다 나쁘다. ONNX를 쓴다면 스레드 2개 지정이 필수다. PyTorch를 2스레드로 줄이면 반대로 느려진다.
- **차수 사이 흔들림이 크다.** 같은 PyTorch 기본 스레드라도 1·2차 6,000자는 p95 약 1,430~1,450이었는데, 재부팅 직후 첫 조합인 3,000자는 4,059로 더 나빴다. 3,000자가 원인이 아니라 재부팅 직후의 부하로 본다. 그래서 위 차이는 표본 하나로 판단하지 말고 재측정 값까지 같이 봐야 한다.
- 각 조합을 섞지 않고 차례로 쟀으므로 시간에 따른 변화(발열 등)가 조합 차이에 섞여 있다.
- 합성 비밀만 썼고, 스크립트는 개수와 시간만 출력한다.

## 7. 기본으로 켜기 전에 남은 일

시간은 필요조건일 뿐이다. 이번 결과만으로 기본값을 바꾸지 않았고, 제품 코드도 수정하지 않았다.

| 항목 | 상태 |
|---|---|
| 모델 품질 | v10 번들은 `production_ready:false`이고, 앙상블 전체에서 평가되지 않았다. 팀의 v9/v10 평가도 남아 있다. |
| 오탐 | holdout-v11 precision 76.15%, 음성 행 39/252. 실제 작업 출력에서는 단서 주변 방식도 git log, package-lock에서 오탐이 나왔다. |
| ONNX 운영 | 어댑터에 ONNX 경로가 없다. `onnx` 패키지는 내보낼 때만 필요하고 런타임은 `onnxruntime`만 필요하다. 모델 버전마다 ONNX 파일(537MB)을 만들고 배포할 곳을 정해야 한다. |
| 미측정 | ONNX로 띄운 실제 워커의 시작 시간과 메모리, 다른 PC, 실제 사용자 작업에서의 입력 길이 분포. |

`promptguard-model` 저장소는 수정하지 않았다. 필요한 변경은 PR 본문에 적었다.
